# The Server Configuration In spec.config

Every behaviour of a Perses server that is not a pod setting comes from its configuration file: where it stores data, who may log in, which dashboards the home page highlights and how long temporary dashboards live. In a `Perses` resource the whole file sits under `spec.config`. This part names the main sections of that file, reads the configuration of a running server from its API, and changes a setting through the resource.

## The sections of the configuration

The operator does not interpret `spec.config`. It writes the block into a ConfigMap and mounts the ConfigMap as the server's configuration file, so the keys are exactly the keys of the Perses server configuration. The sections you meet most often are these:

| Section | What it controls |
| --- | --- |
| `database` | Where the server stores resources: `file` (a folder and an extension) or `sql` (a MySQL-compatible database) |
| `security` | Read-only mode, authentication, authorization, cookies and the encryption key |
| `provisioning` | Folders of resource files the server loads at start and reloads on an interval |
| `frontend` | What the user interface shows, such as an information banner and important dashboards |
| `ephemeral_dashboard` | Whether temporary dashboards are allowed and how long they live |
| `schemas` | The folder of plugin schemas the server uses to validate dashboards |

Two rules follow from this design. First, the operator cannot warn you about a wrong key, because it does not read the keys. The server is the one that refuses a configuration, and it does so when it starts. Second, `spec.config` is the complete file, not a patch. A key you leave out gets the server's default, and the operator does not add keys for you except where the resource has a dedicated field.

## Read the configuration a server uses

Before you change a setting, read what the running server uses now. The Perses API returns its public configuration at `/api/config`. Secrets such as the encryption key are not part of it. Ask the server in your playground from the `tester` pod:

<!-- astrona:playground:renew -->

```sh
kubectl -n observability exec deploy/tester -- sh -c \
  'curl -s http://perses.perses:8080/api/config | jq "keys"'
```

The list shows the top-level keys the server reports. Look at the database section next:

```sh
kubectl -n observability exec deploy/tester -- sh -c \
  'curl -s http://perses.perses:8080/api/config | jq ".database"'
```

The answer has the folder `/perses` and the extension `yaml` that the `Perses` resource declares. This is the check you repeat after every change: the resource says what you asked for, and `/api/config` says what the server runs.

## Change a setting through the resource

Turn on ephemeral dashboards. An ephemeral dashboard is a temporary dashboard that Perses deletes after a time to live, used for previews and for dashboards generated by a tool. The setting has two keys: `enable` and `cleanup_interval`, how often the server looks for expired ones.

Save this as `perses-config.yaml`:

```yaml
apiVersion: perses.dev/v1alpha2
kind: Perses
metadata:
  name: perses
  namespace: perses
  labels:
    app.kubernetes.io/instance: perses
spec:
  image: docker.io/persesdev/perses:v0.54.0
  containerPort: 8080
  config:
    database:
      file:
        folder: /perses
        extension: yaml
    ephemeral_dashboard:
      enable: true
      cleanup_interval: 1d
  storage:
    emptyDir: {}
  resources:
    requests:
      memory: 128Mi
    limits:
      memory: 512Mi
```

Apply it:

```sh
kubectl apply -f perses-config.yaml
```

Then check the result:

```sh
kubectl -n perses rollout status deployment/perses
kubectl -n observability exec deploy/tester -- sh -c \
  'curl -s http://perses.perses:8080/api/config | jq ".ephemeral_dashboard"'
```

The operator changed the ConfigMap. A changed ConfigMap alone does not restart a pod, so the rollout command is the way to see whether the operator also restarted the server; if it did not, delete the pod with `kubectl -n perses delete pod --all` and let the Deployment create a new one. The server reports the new setting only after it has read the new file, which proves the file reached it.

## What a refused configuration looks like

Now make a mistake on purpose. A value of the wrong type is enough, because the server parses the file when it starts. Patch the cleanup interval to a text that is not a duration:

```sh
kubectl -n perses patch perses perses --type merge \
  -p '{"spec":{"config":{"ephemeral_dashboard":{"cleanup_interval":"tomorrow"}}}}'
kubectl -n perses get pods
```

If the server refuses the value, the new pod does not become ready. Read its log to see the server's own explanation:

```sh
kubectl -n perses logs deploy/perses --tail=20
```

The operator reported success when it created the objects, because the resource itself was valid. The server is what refused the file, so the cause is in the pod log, not in the conditions of the `Perses` resource. The old pod keeps serving while the new pod fails, which is why the API can still answer with the old configuration. Put the correct value back:

```sh
kubectl -n perses patch perses perses --type merge \
  -p '{"spec":{"config":{"ephemeral_dashboard":{"cleanup_interval":"1d"}}}}'
kubectl -n perses rollout status deployment/perses
```

## Keeping the file readable

A long configuration is easier to review when `spec.config` holds only the keys you set on purpose. Leave out keys whose value is the default. Keep secrets out of it: the encryption key and database passwords have file variants in the configuration (for example `password_file`), which read the value from a mounted Secret, so the ConfigMap holds a path and not a password. The ConfigMap is readable by anyone who may read ConfigMaps in the namespace.

You can now name the sections of the configuration, read what a server runs from `/api/config`, change a setting through the resource and find a refused configuration in the pod log. The open question is what the resource sets for the pod around the server.

## Common pitfalls

> [!WARNING]
> - **Trusting the conditions after a configuration change.** The operator accepts any `spec.config`. The server's log shows whether the server accepted it.
> - **Putting a password in `spec.config`.** The block becomes a ConfigMap. Use the file variants of the keys and mount a Secret.
> - **Expecting a partial `spec.config` to merge with the old one.** The block you apply is the whole file.
> - **Reading the resource instead of the server.** Compare `/api/config` with the resource after each change.
